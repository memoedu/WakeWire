# RemNote 知乎文章定时发布

「每日知乎短文」和「知乎文章」沿用同一发布程序，各用一个 Windows 任务、配置目录、锁和回执。同一正式时段每条队列各最多发布一篇。文内直属节点用 `%` 标记，文外节点同时加对应文档标签和 `%`。两条队列均保留首次发布时间，「知乎文章」省略篇号和天数。

「知乎文章」配置使用 `"columnRouting": "tags"`、`"requirePreflight": true` 和本队列自己的 `publishedTagRemId`，省略 `columnId`、`seriesStartDate`。发布前按节点直接标签的全文匹配知乎账号的专栏列表，核验匹配专栏的身份、名称和管理权限。多个标签分别与不同专栏同名时，这些专栏会随同一篇文章提交。没有匹配的标签时，文章发表在个人账号下。审核冻结专栏 ID，正式提交前用冻结原稿重新核对匹配结果，公开回读确认完整的目标专栏集合后才归档。短文仍按固定专栏配置。

文章队列使用 `WakeWire - RemNote Zhihu Library Articles`。给任务安装脚本传入独立的 `-Config` 和 `-TaskName`，需要先验收时用 `-Disabled`。本地预览可指定准确来源，例 `node dist/workflows/remnote-zhihu-cli.js preview <absolute-config.json> <source-rem-id>`。

将配置指定的 RemNote Document 直属第一层母节点中行首单个 `%` 标记的节点及其完整物理子树发布为一篇知乎文章。标记母节点自身的可见文字作为文章标题，其下完整物理子树作为正文。用固定 Rem ID 绑定真实 Document，同一 Document 改名不改变发布范围，也不匹配同名普通节点。按直属母节点顺序处理，不进入未标记母节点内部查找 `%`，正文中以 `%` 开头的节点保留为正文，不作为独立稿件。不附带父项或兄弟项，不摘要、改写或添加话题。母节点 `%%` 暂停该稿件；「已发布」子树完全排除。

配置 `publishedTagRemId` 后，同一次扫描还会按该 Document 的精确 Rem ID 查询直接使用它作 tag 的节点。外部母节点必须同时具有这个 tag 和行首单个 `%`；只有 tag 时保留为待写内容，只有 `%` 时不扩展到无关位置。母节点自身作为标题，完整物理子树作为正文；支持其他 Document 内及知识库根级的位置。按原 Document 内容优先、外部节点 ID 稳定排序并入同一队列，共享原时段、锁和去重回执。Document 内的同一节点即使也带 tag，仍只按原 Document 流程处理一次；嵌套就绪来源、截断的 tag 搜索及异常分页会被拦截。

外部来源成功发布并核验后保留原位置：先添加 `publishedTagRemId` 指向的「已发布」tag 并回读，再移除 Document 的触发 tag 并回读，最后清除 `%` 并再次核对全文、层级、原父节点和其他 tag。两个 tag 均按节点 ID 操作，完成 tag 必须确实是该 Document 直属的「已发布」节点，不按同名 tag 猜测。中断后只继续完成 tag 切换或去标记，不再次发文；原 Document 内来源仍沿用整棵移动归档。

## 发布与恢复

北京时间每天 09:30、15:30、20:30 准备草稿，11:30、17:30、22:30 正式发布。Windows 计划任务直接运行 `scripts/run-remnote-zhihu.ps1`，再调用本 CLI。每条队列每个时段最多发布一篇，其余顺延。允许当次任务在 15 分钟内启动，错过窗口不补发。

决策工作台「运行与调度」复用同一个 Windows 任务的身份、启停与运行入口，不新建定时器。工作台绑定配置中的 `reportFile` 指向本流程 `last-run.json`，用于回读最新业务状态；运行失败也写入新的错误状态与完成时间，避免旧成功回执掩盖本次失败。

准备阶段核对 Document 身份、完整子树及原父节点，并冻结通过审核的版本。启用提前审核后，到点发布只使用该快照和已知知乎草稿 ID，不连接、扫描或读取 RemNote；提交前仍核对知乎账号、专栏、云端草稿全文与格式、审核时段及冻结版本。提交前将不可自动重放的记录落盘并同步到磁盘；任何超时、结果不明或没有明确文章 ID 的响应都会保留记录、停止后续发布，不能通过再次运行 CLI 重发。需要人工核对后恢复时，先找到实际公开内容；不得删除记录绕过去重。

取得 ID 后回读 `https://zhuanlan.zhihu.com/p/<id>` 对应的 API 内容，核对 ID、作者、标题、全部可见文字、列表层级、强调、链接目标和指定专栏的已接受归属。通过后先落盘公开 URL 与 `verified` 状态，再独立尝试 RemNote 归档；知识库切换或断开不阻止文章发布，工作台区分“已发布、归档待完成”与“发布失败”。连接恢复后，后续准备或恢复运行仅补归档。归档时核对冻结快照后将原 Rem 节点及完整子树移动到 Document 的「已发布」下，回读后去掉根节点 `%`，保留原 ID、子树、内部引用及结构。冻结之后原稿有修改或移动时保留用户改动，停止归档，不反向改写原稿，也不重复发文。已知 ID 的发布结果继续只读核验，结果未知则停止。

文章保留多行文字、Markdown 强调、链接和真实嵌套列表。空叶节点在正文内容组之间转为空段落分隔，不生成空项目符号；同级内容组首尾的空编辑占位不输出，内部连续空节点保留各自间隔。节点内单换行转为 `<br>`，连续换行保留相应行距，不能依赖 HTML 中会折叠的普通换行。带子树的空容器保留子树层级但不生成空项目符号。回读按可见列表深度、空段落位置、节点内换行及强调/链接所在文字位置核验，允许知乎将子列表移到父 `li` 外侧和将 `strong` 转为 `b`，不把等效 DOM 变化误判为内容变化；原始 HTML 作为文字转义，不允许脚本执行。Rem 内部引用只输出可见文字，不跟随读取引用目标。媒体、portal、未解析引用和重叠标记保留原位并报告，不以漏内容的版本发布。标题必填、禁止换行、最多 100 字；正文必填、9～100,000 字。超限时停止，不自动删减、补写或拆分。相同标题与可见正文的重复来源也会被拦截。

正文保留原稿内部的分段空行；正文结束后固定追加一个空段落，再依次放置 `第N 篇 | day D` 和 `首次发布时间：YYYY.MM.DD HH:mm` 两段，标题只保留原文章名称。篇次与日期信息不占标题字数。采用上海时区首次发布提交时刻；篇次、day 与时间和提交回执一同落盘，正式发布时根据真实提交日和已发布篇次重新计算。后续只读核验、归档恢复不刷新该时间；旧已归档文章不自动改写。审核草稿使用 `首次发布时间：待发布`，认可后正式提交时替换为实际时间。去重只比较源正文，不受发布尾注变化影响。

RemNote 的 `$...$` 行内公式及 `$$...$$` 公式转换为知乎原生 equation 图片，LaTeX 原文经 URL 编码放入知乎公式地址，并保留于 `alt`；转义美元符号、行内代码及代码块保持文字。回读把公式模式、LaTeX 与出现位置纳入布局对照，不能因图片没有文本节点而漏检公式；超链接保留原目标地址。

文章元数据读取启用本地 MCP 的 `renderNativeMarkdown`，正文另按节点读取 `personalwebsite_richtext` 原生片段，直接转换粗体、原稿斜体、代码、超链接和公式，不经 Markdown 重解析。这样粗体末尾带空格也不会输出为字面双星号。原生格式片段参与源新鲜度校验；不支持的内容停止处理。草稿核验优先读取实际持久化的 `/draft`，不把另一接口返回的未清洗内容当作最终输入。知乎会清空公式图片的 `src`，但保留 `eeimg` 与 `alt` 并在编辑器中构建 MathJax 公式；对照比较这些原生公式数据。

RemNote 原生下划线按精确文字范围转换为知乎 `<u>`，可与粗体、斜体、换行和普通超链接组合。若旧富文本接口拒绝原生 `u` 标记，文章适配器从同一 MCP 的既有 `personalwebsite_nodes` 只读快照恢复受支持的文字、标记、链接、公式与引用；仍核对精确节点身份，未知字段或无法解析的引用继续停止，不删除标记以换取通过。下划线起止位置参与冻结指纹和草稿／发布格式回读，正文文字相同但下划线缺失或移位也不能通过。普通文本中的 `_` 不视为下划线。

旧富文本接口拒绝原生 `code` 标记时，同一快照路径会保留原有行内代码的精确范围。

Emoji 保留原始 Unicode 字符及组合序列。知乎按原生正文呈现，审核比较包括组合符、肤色、变体选择符及旗帜字符。独立 Mermaid 源码节点用本地 Mermaid 渲染为 PNG，图内文字和箭头沿用原稿。支持独立 Mermaid 围栏及只有图定义的多行节点。图片按原顺序进入知乎标准图片块，正文中相邻列表保持原层级。排版回读校验每张图的媒体身份和顺序。知乎侧编辑含图片的稿件时，反向同步会保留两端并报告无法自动投影的图片。

Mermaid 图片使用 720 像素宽的画布和两倍像素密度。绘图居中，同字号使用相同缩放，图的高度随内容变化。宽图或长图超出画布可用范围时等比缩小。画布宽度固定，避免知乎按正文宽度显示时把窄图的文字放大。

启用 Mermaid 前，在队列配置中设定 `diagrams.modules`（安装 Mermaid 和 Playwright 的目录）、`diagrams.browserExecutable`、`diagrams.node`、`diagrams.cache` 及精确的 `diagrams.mermaidVersion`、`diagrams.playwrightVersion`。当前 Windows 验收使用 Mermaid `11.17.2`（MIT）和 Playwright `1.63.0`（Apache 2.0）。页面在隔离的无头 Chromium 中渲染。`preview` 只生成本机图片。草稿准备复用 `pyzhihu-cli` 的图片存储和状态回读，按当前知乎编辑器协议确认上传完成，再缓存媒体身份。正式发布按该身份获取新鲜的私有图片链接，检查图像身份和顺序。配置、图片缓存和凭据留在本机数据目录。

独立引用在提前审核、草稿转换和正式发布时自动转换为知乎原生 `link-card`。范围是没有子节点、没有换行的叶节点：只有一个完整链接或裸 URL，或者最多 20 字的简短说明加冒号再接一个链接，例如“原文：链接”“译文：链接”。保留说明文字与原目标地址；卡片输出到所有列表之外，再恢复后续正文的原层级。包含额外正文、多个链接、换行、代码、公式、标准艾特或子节点的内容保持原样；句子中内嵌的普通超链接不转换。链接标题若显式带下划线，保留原下划线超链接，因为知乎卡片标题不能保留该文字样式。该规则复用既有原生卡片表示，不生成截图或第三方跳转卡片。

保存云端草稿后及正式发布前后，全文和格式对照同时核验卡片类型、数量、顺序、标题、原始目标地址及独立块位置。封面、站点信息和赞同数等知乎自动补充的元数据不参与源正文比较。卡片被清洗为普通链接、丢失或改指目标会停止该篇发布，问题沿用工作台原审核反馈入口。升级后已审核版本若与新转换结果不同，需重新审核，不能覆盖人工编辑或绕过原草稿 ID 与提交围栏；既有已发布文章不批量改写。

编辑器最多显示五层列表。源正文有六层时，将文章一级节点输出为段落标题，其后五层输出为列表。源正文超过六层时，继续保留五层原生列表，超出的后代在对应的末层母项内另起一行，每深入一层增加两个全角空格，以实心黑圆点 `•` 标记，依原顺序保留各节点及富文本。这是视觉层级的补偿表示：长句自动换行后的后续行会退回原生母项缩进，已接受这一显示限制，不改写或压平 RemNote。回读同时比较全角空格、圆点、换行、完整文字和强调/链接/公式；丢失或改变补偿缩进时停止发布。原生层级范围内的排版不变。无法明确挂接的超限结构仍停止并返回审核问题。空段落输出到列表容器外侧，再恢复后续列表深度，避免编辑器调整空段落时改变其后内容缩进。

正文存在至少一个非空的知乎原生章节标题（`h2` 或 `h3`）时，草稿和正式发布自动开启知乎原生目录；没有这种标题时不开启，不为生成目录改写正文或新增标题。草稿保存回读核对 `settings.table_of_contents.enabled`，正式提交携带 `contentsTables.table_of_contents_enabled`，新发布回执保存预期目录状态并在发布后独立核验，未知结果恢复仍沿用原文章身份。目录设置不一致时停止，不重复发布。旧回执未记录目录预期值时继续按原有内容及身份规则核验。

显式 `draft ... --new-version` 会保留已知旧云端草稿，另存新稿，并将旧记录移入本机 `previousDrafts`；普通重试仍复用同一 ID。未知的创建结果始终禁止重建，正在创建的已知 ID 即使带此参数也先恢复原记录，不再创建副本。

配置 `aiGeneratedTagRemId` 后，按精确 tag ID 将对应节点及全部后代视为 AI 内容：只在最外层标记母节点前放一个紫色原生公式短标识 `AI`，不自动添加斜体。子层级不重复添加标识，嵌套同类标签也不重复；原稿已有的文字格式保持原样。整篇母节点本身带 tag 时，在正文开头放一次标识，标题保留知乎原生纯文本形式。正文和链接仍是原生文字，公式原有 LaTeX 保留。标记范围参与审核快照校验；启用提前审核后，正式发布沿用已冻结的标记范围。自定义 HTML 文字颜色会被知乎清洗，因此仅短标识使用 LaTeX 色号，不将整段正文转换为公式。

## 发布前审核与原调度合并

因每时段一篇的额度而排队的自动审核稿，可在后续正式窗口沿用原已审核快照：必须能核实原审核时段确有另一篇文章已发布，草稿 ID、冻结指纹和知乎正文仍匹配，且没有后续撤回、冲突或单篇审核失败。延续记录保留原审核时间及来源时段，不伪造新的审核。这样，下一轮 RemNote 扫描暂时失败不会单独取消已审核队列的发布资格；人工验收草稿及结果不明的提交仍不允许自动重放。

审核阶段先对已知发布 ID 做只读恢复，确认后同步关闭旧草稿的待发布状态，再处理归档与新稿审核。回执与摘要分别报告本次新发、过往文章核验和归档待办；子流程失败只透传经过白名单处理的错误类别，不记录凭据或远端响应正文。

知乎读取、RemNote 全量扫描或来源快照遇到明确的临时连接错误时，间隔两秒只重读一次。登录失效、语义冲突和未知写入结果不在重试范围；创建、正文写入和发布不使用此重试器，未确认的写入仍保留原 ID 和围栏等待核对。

设置 `requirePreflight: true` 后，现有 Windows 任务保留原身份，增加每天北京时间 09:30、15:30、20:30 的草稿审核；11:30、17:30、22:30 仍每个时段最多发布一篇。统一 `tick` 命令在正式窗口发布已审核的冻结版本，其余时刻审核下一发布时段；工作台“立即运行”在窗口外因此可用于重新审核。显式 `audit` 不发布，可先恢复已发布稿件的待办归档。原 `run` 也受配置中的审核约束，不能绕过。配置 `knowledgeBaseId` 锁定准备和归档所需的知识库；切换到其他知识库会阻止这两个阶段并反馈，不影响已审核稿件发布，也不根据同名内容改变来源。

审核覆盖原来源边界、完整正文、原生公式、列表层级、空行、强调、超链接、标准艾特、账号及专栏条件，不进行 AI 内容评判或改写。逐篇保存真实知乎草稿并回读核验，沿用创建围栏与已知 ID，不重建未知结果。已由用户创建且待人工认可的草稿、用户编辑过的云端草稿保持原样并返回问题。通过记录绑定冻结源版本、草稿 ID、提及身份及发布时段；发布阶段只核对已存快照和云端草稿，晚加入的稿件没有有效审核时不进入发布队列。冻结之后若要撤回本次发布，通过工作台命令处理待发布记录；只修改 RemNote 原稿不会自动改变已审核的发布版本。

`state.json` 持久保留逐篇审核记录；同一篇重新审核成功才解除原问题，重新扫描时撤回触发标记视为撤稿，已完成发布不再提示等待发布。`last-run.json` 的 `feedback` 包含审核时间、目标时段、文章标题、问题、草稿或已发布链接及待办归档信息，不包含全文。后续正常空跑保留未解决的问题。该反馈沿用工作台同一业务绑定与日报入口，人工命令发送到该业务配置的原生 Thread；不创建另一工作流或另一传输机制。

```powershell
node dist/workflows/remnote-zhihu-cli.js audit <absolute-config.json>
node dist/workflows/remnote-zhihu-cli.js tick <absolute-config.json>
```

## 客户端与凭据

正文中的 `@姓名` 使用知乎原生 `member_mention` 节点，写入真实账号 hash 与 hovercard，并将账号身份纳入格式核验。`mentionBindings` 可保存用户已经确认的姓名与账号 ID；每次转换仍通过当前登录态核对账号。未绑定姓名先进行有限分页的用户搜索，只采用完整结果中唯一的同名账号并再次核对档案；重名、缺失、未完成的分页或身份变化会停止，不能退回普通文字。邮箱、代码、公式和原有超链接不按普通提及文本重解释。审核后及最终提交前再次比对提及身份，防止目标变化。

已核验官方 `zhihu-cli` 0.6.1 的 `capabilities`，该版本没有文章发布命令。官方发布 Skill 是另一条 OpenAPI 路线，需要独立发布凭据，不能把官方 CLI 的 Access Secret 擅自视为发布授权。

本流程调用维护中的 [BAIGUANGMEI/zhihu-cli](https://github.com/BAIGUANGMEI/zhihu-cli) 的 `ZhihuClient`（PyPI 包 `pyzhihu-cli==0.2.4`），复用其 CSRF、草稿及统一内容发布能力。纯文字文章也使用知乎当前网页编辑器的 `POST /api/v4/content/publish`，传入 `action: article`、固定草稿 ID、正文和专栏数组；不再使用该版本纯文字分支中的旧 `PUT /articles/<id>/publish`。发布前检查专栏管理权限，发布后必须回读到同一专栏的 `accepted` 归属。创建草稿取得 ID 后，在任何正文写入和公开发布前先保存该 ID；结果不明时仅按原 ID 只读核验，禁止重新提交。文章已发布但专栏尚未接受时保留文章 ID，不重复发文或提前归档。安装到本机独立 Python 环境：

```powershell
python -m venv <runtime-directory>
<runtime-python> -m pip install -r scripts/zhihu-requirements.txt
```

客户端适配器每次读取现有 Chrome Cookie 同步快照，向 `https://www.zhihu.com` 与 `https://zhuanlan.zhihu.com` 发送匹配域名、路径和有效期的 Cookie。只有准备文章图片时，允许 `https://api.zhihu.com` 的图片登记、处理确认和状态查询请求。请求禁止重定向，不复制或另存 Cookie。超过 15 分钟未同步、退出账号、账号与配置不符时停止。日志不打印 Cookie、请求头、远端响应正文或源笔记正文。

## 本机配置与命令

真实 Document ID、账户 ID、Cookie 快照、Python 环境及回执只保存在本机应用数据目录，不进入 Git。配置示例：

```json
{
  "documentRemId": "<exact-document-id>",
  "documentTitle": "<display-name-only>",
  "mcpUrl": "http://127.0.0.1:<port>/mcp",
  "python": "<absolute-runtime-python>",
  "cookieSnapshot": "<existing-local-chrome-cookie-snapshot>",
  "accountId": "<verified-zhihu-account-id>",
  "columnId": "<verified-managed-column-token>",
  "seriesStartDate": "<YYYY-MM-DD-in-Shanghai>",
  "publishedTagRemId": "<exact-published-child-rem-id>",
  "aiGeneratedTagRemId": "<exact-ai-generated-tag-rem-id>"
}
```

```powershell
node dist/workflows/remnote-zhihu-cli.js check <absolute-config.json>
node dist/workflows/remnote-zhihu-cli.js scan <absolute-config.json>
node dist/workflows/remnote-zhihu-cli.js preview <absolute-config.json>
node dist/workflows/remnote-zhihu-cli.js draft <absolute-config.json> <source-rem-id>
node dist/workflows/remnote-zhihu-cli.js draft <absolute-config.json> <source-rem-id> --new-version
node dist/workflows/remnote-zhihu-cli.js approve-draft <absolute-config.json> <source-rem-id>

pwsh -NoLogo -NoProfile -File scripts/install-remnote-zhihu-task.ps1 -Config <absolute-config.json>
```

`check` 为只读扫描及登录核验；`scan` 只读计数；`preview` 将第一篇待发布内容转换为本地 HTML，不触碰知乎草稿或修改 RemNote。`draft` 使用真实知乎登录态创建并保存云端草稿，回读标题、全文与布局，返回真实编辑器链接；重复运行更新同一草稿，不另建副本。草稿结果不明时保留记录，禁止自动重建。云端已被作者修改时停止并保留改动。草稿对应的来源保留在 RemNote 原位，处于待验收状态时定时扫描跳过该来源，其余内容仍按序处理。只有用户明确认可后才执行 `approve-draft`，将该草稿恢复为可发布；此命令本身不发布。启用提前审核后的正式 `run` 复用已认可草稿的同一 ID，发布前核对冻结快照、云端内容及当日标题，不读取 RemNote，也不覆盖作者后续修改的云端草稿。

配置 `seriesStartDate` 时，云端草稿和正式文章使用原始标题；正文末尾空一段，再放 `第N 篇 | day D` 和首次发布时间。篇数按专栏已发表文章数、既有篇号与本地已发表回执的最大值递增；草稿不占正式篇数。day 按上海时区从配置起始日期计算自然日，起始日为 day 1；同一天多篇共用 day 数。实际发布前重新计算，草稿中的编号只是当时预览。原始标题超过 100 字即停止。

## 手动单向同步

复用现有配置、登录态、知识库校验和 `run.lock`，不另建定时任务。两个命令默认只生成只读计划，带 `--apply` 才写入；均禁止调用发布接口。每次使用新的绝对路径作为验收目录。

```powershell
node scripts/zhihu-sync.mjs pull <absolute-config.json> --out <absolute-bundle> --apply
node scripts/zhihu-sync.mjs push-drafts <absolute-config.json> --out <absolute-bundle> --bindings <absolute-bindings.json> --apply
```

`pull` 只读取本流程已归档回执对应的公开文章，不枚举或导入账号的其他历史文章。沿用原 Rem ID 和父节点映射，保存新增内容、明确的文字修改与结构调整；不删除来源。歧义匹配、远端删除、本地相对上次基线已有修改、未支持的媒体或写入格式均停止。正文快照、逐步恢复记录和独立回读保存在本地验收目录，验收后的双端基线保存在配置旁的 `sync-state.json`。平台生成的 AI 标识、篇号及发布时间作为发布元数据保存，不重复注入原稿。知乎卡片在 RemNote 中投影为同标题、同目标地址的原生超链接。

`push-drafts` 的绑定文件为 `[{"sourceId":"<source-rem-id>","draftId":"<existing-draft-id>"}]`。仅接受仍满足原扫描边界的来源及本人尚未发布的草稿，保存原云端快照后覆盖同一 ID，不创建新草稿。保存后逐项比较文字、富文本、公式、列表、链接、标题及目录，再进入原有提前审核流程；反馈写回既有 `last-run.json`，不改变正式发布时间。作者后续在知乎修改草稿时，原发布前校验仍会阻止覆盖或发布未审核版本。

回读可将本流程生成的“全角空格＋实心圆点”溢出行还原为原始层级，行内下划线、粗体、公式、链接和普通换行分别保留；只识别原生第五层之后的约定标记。当前 RemNote 写接口尚未支持的新增格式（例如新增下划线）会在第一笔写入前停止，原有且未改变的格式保持原节点。不能把仅解析成功描述为写入成功。

## 共同基线的受控双向同步

配置 `controlledSync: true` 后，原 `audit` / `tick` 审核阶段先比较本机 `sync-state.json` 中的共同基线、最新 RemNote 子树和知乎内容。仍复用同一 Windows 任务、工作台业务绑定、排他锁和反馈文件，不增加调度器。处理范围只包含本流程已有回执及草稿绑定，账号其他历史文章不纳入。

- 单边修改：知乎的内容变化回写原 RemNote 节点；RemNote 的变化更新原待发布草稿，或为已发布文章准备修订预览。
- 双边修改：按原 Rem ID 合并不同节点上的文字或格式变化；同一节点的相同结果视为收敛，不同结果返回冲突。存在不能确定身份的替换、删除或无法安全组合的结构变化时停止该篇，保留双方，不以修改时间决定覆盖关系。
- 已发布文章：自动保存并核验修订预览，冻结来源、正文、标准艾特身份和目标时段；审核通过后在原正式时点更新原文章 ID。篇号、首次发布时间及专栏归属保持原有值。预览草稿独立保存并复用，不作为新文章发布。
- 正式阶段：沿用 11:30、17:30、22:30 的窗口；原新稿规则不变，每个窗口另最多更新一篇已审核旧文章。来源和布局在审核时冻结，正式更新不连接 RemNote。提交前重新核对公开原文和预览草稿，作者在审核后的知乎编辑会阻止该次覆盖。
- 基线推进：仅在两端内容相符且回读通过后推进。已保存修订预览并不表示公开原文已更新，也不能提前将公开基线替换为待发布版本。
- 反馈与恢复：冲突和待发布修订合入原 `last-run.json` 反馈；原工作台入口继续将命令投递到原 Thread。修改结果不明时先保留原文章 ID、预览 ID、逐步回执和提交围栏；后续只读核验，禁止再次提交未知结果。

修订时冻结文章已收录的专栏集合。多专栏修订先核对知乎编辑状态中的原文章内容和专栏，编辑接口返回完整列表时提交全部，接口只返回主专栏时沿用主专栏提交。若回读确认正文已更新、主专栏仍在，但缺少原有的其他专栏，流程只补收录缺少的专栏；每一步先落盘，结果不明时继续回读。正文与原专栏集合均核验通过后才推进共同基线。对审核后用户自行改变的专栏归属停止处理。

保真边界仍有效：新增下划线等当前 RemNote 写入口尚不支持的格式会在第一笔写入前停止；现有下划线可以保持原节点并正常向知乎转换。无法保留的原文封面或评论设置也会停止更新，不能静默重置。用户显式保留为人工验收的草稿继续保持原验收边界。

只有 `run` 会在指定窗口发布，窗口外仅恢复已有记录。`adopt` 用于用户明确指出已手动发布的文章：核对完整正文、可见布局、作者与专栏后，登记实际公开标题和 URL，将原子树归档；它不会新建或修改任何知乎文章。保存过的草稿若由用户手动发布，后续运行按同样条件核验并归档，不再发一次。已有回执冲突或对照不符时停止，不靠移除 `%` 隐藏问题。配置目录保存 `state.json`、`last-run.json`、`preview.html` 和 `preview.json`。运行使用进程排他锁，死进程残留锁可恢复，活进程持锁时拒绝并行。

转换器直接输出知乎原生的列表表示：子列表放在已闭合的父 `li` 之后。标准 HTML 的 `<li>父项<ul>子项</ul></li>` 虽然网页显示正常，但知乎编辑器导入时会在父项闭合处额外插入空段落，不能作为发布输入。API 回读中的文字和语义列表一致也不足以证明编辑器导入一致；真实验收需将编辑器渲染后的内容块逐一对照源节点，比较空行数量与位置、项目深度、文字及节点内换行。

任务以当前登录用户的 Limited 权限隐藏运行，禁止重叠实例，保留实际 Node 子流程的退出码。失败最多间隔 5 分钟重试两次；CLI 的窗口限制和已落盘回执仍约束每次重试，不会再次提交未知结果。注册任务不会立即执行发布。需 Windows 用户已登录及现有 Chrome 登录态同步可用；准备与归档另需正确知识库的 RemNote MCP 在线，发布已审核稿件不需要 RemNote 在线。不依赖 ChatGPT 桌面端中的 Codex 保持开启。暂停时停用该 Windows 计划任务，保留本机回执。恢复连接沿用已有 RemNote MCP 启动入口，不重启 RemNote 或用户正在使用的应用。不得通过删除未知结果记录、临时另发、扩大到其他 Document 或补发错过时段绕过限制。
